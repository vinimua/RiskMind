# 从 Claude Code 到 RiskMind：上下文、记忆与压缩的工程实践

> 核对日期：2026-11-25。本文结合 Claude Code 官方公开文档与当前仓库代码。官方行为、工程解释、RiskMind 实现分别说明；不把推测写成 Claude Code 未公开的内部算法。代码位置以函数名为准，行号可能随修改变化。

## 1. 为什么“保存了”不等于“模型记住了”

假设用户先说“只分析，不启动调查”，随后助手读取数千行材料，最后用户问“继续”。数据库即使保存了第一句话，只要本次请求没有把这条约束或准确摘要送给模型，模型就无法可靠使用它。

因此需要区分三个问题：记录在哪里保存？本次选哪些内容发送？遗漏细节如何重新读取？它们分别对应持久化、上下文组装和回查。

模型上下文是本次请求的数据集合，不是数据库，不是全部历史，也不是长期记忆本身。一次新请求需要由应用重新组装所需材料。摘要只是其中一种材料。

| 对象 | 例子 | 当前 RiskMind 的职责归属 |
| --- | --- | --- |
| 本次上下文 | 规则、问题、摘要、近期消息、工具声明和结果 | 模型请求组装与预算 |
| 会话记忆 | 当前目标、已讨论决定、近期问答 | 会话摘要与原始聊天记录 |
| 长期个人记忆 | 用户稳定偏好和明确纠正 | 独立个人笔记 |
| 调查轮次事实 | 正式计划、执行结果、Observation | 阶段账本与案件记录 |
| Skill | 调查步骤、解释方法 | 方法文件目录与按需读取 |
| 项目知识库 | 背景文档、案例线索 | 知识检索系统 |

调查轮次与聊天轮次不同：前者包含多个任务及其工具执行，后者通常是一条用户消息与对应助手回答。项目没有必要再复制一份“本轮记忆”来保存已有账本事实。

## 2. Claude Code 公开说明了什么

### 2.1 上下文不止包含对话

Claude Code 的上下文包括历史交流、文件内容、命令输出、指令和已加载方法资料。工具不断带回内容，窗口会逐渐增长。它既提供自动压缩，也提供 `/compact` 和 `/context`。这是产品公开行为，而非本文推导的算法。[官方上下文说明](https://code.claude.com/docs/en/how-claude-code-works)

这解释了为什么只截取最近几条聊天消息不够：Agent 的大头可能是工具输出。RiskMind 因此分别处理聊天历史、Planning 读取材料和 Observation 结果项，而不只截断聊天正文。

### 2.2 原始转录与当前输入分开

Claude Code CLI 公开使用本地 JSONL 保存会话，提供恢复和导出入口；JSONL 内部记录格式会变动，不能把它当稳定集成协议。保存记录和发送内容是两层职责。[官方会话说明](https://code.claude.com/docs/en/sessions)

RiskMind 对应使用 PostgreSQL：聊天记录、读取交互、Planning 事件和执行账本分别保存。存储形式不同，借鉴的是“原文与本次视图分离”。记录保留仍应服从权限和数据保留策略，不能把“可回查”解释成永不删除或永久有权读取。

### 2.3 压缩、重载与长期记忆不同

官方说明 `/compact` 用摘要替换当前历史；大部分启动材料会重新加载。不能由此推断所有曾读文件、全部 Skill 正文或每项后台状态都一定完整恢复。[官方窗口示例](https://code.claude.com/docs/en/context-window)

工程上应把“重新组装必要规则和当前任务”与“重新取得全部细节”分开。后者需要定位和读取入口。摘要本身有损，不能称为可逆压缩。

### 2.4 长期记忆是独立笔记

Claude Code 将人工指令文件与自动记忆区分：前者表达规则，后者积累偏好和纠正等经验；自动记忆以笔记方式跨会话使用，不等同于把全部聊天历史加载进下一会话。具体加载限制随产品版本变化。[官方记忆说明](https://code.claude.com/docs/en/memory)

RiskMind 借鉴独立笔记与按需读取，但用数据库承担用户隔离、修订和并发控制。不能据此声称两者拥有完全相同的维护算法。

### 2.5 缓存不等于记忆

Prompt Caching 复用已处理前缀，降低重复处理开销；它不替应用选择材料，也不使逻辑上下文无限变大。[官方缓存说明](https://code.claude.com/docs/en/prompt-caching)

RiskMind 尚未实现专项缓存配置和命中率验收。供应商可能自动缓存，但不能因此将其标为项目已完成能力。

### 2.6 哪些“内部实现”不能断言

“Microcompact 的精确选择算法”“每完成一步就维护 facts/decisions/todos”“固定次数的 prompt-too-long 重试”“固定的 rehydration 字段”不能仅凭上述公开文档认定为 Claude Code 的源码实现。渐进处理可作为我们的工程设计，但精确阈值、字段和状态机必须以项目代码或明确版本的一手证据为准。

官方确实说明：反复压缩后窗口仍立即填满时会停止，而不是无限循环。[窗口耗尽处理](https://code.claude.com/docs/en/how-claude-code-works)

## 3. RiskMind 的实际调用链

```text
保存当前用户请求
  → 读取旧摘要、未覆盖历史、个人记忆目录
  → compact_history：按整体请求预算处理旧历史
  → ChatAgent.decide：回答或请求读取
      → read_memory / read_chat_history
      → 保存本次读取配对
      → 继续调用模型
  → 保存最终回答及可选记忆维护候选
  → 独立处理个人笔记维护
```

入口代码见 [entrypoints.py](../backend/src/risk_platform/entrypoints.py)，模型交互见 [conversations/agent.py](../backend/src/risk_platform/conversations/agent.py)。读取循环是有界的；不是新增一个业务主图，也不绕过调查流程执行动作。

个人笔记维护发生在回答保存之后。维护候选只是“可能需要修改笔记”的建议，不是已经记住，更不是审批事实。维护失败不会撤销已经保存的回答。

## 4. 先算完整请求，再决定压缩

核心实现位于 [token_budget.py](../backend/src/risk_platform/core/token_budget.py)。`request_tokens(messages, tools)` 将消息及工具声明纳入估算。

可用输入应满足：

```text
可用输入 = min(应用输入限制, 模型窗口 - 输出预留 - 安全余量)
```

当前聊天默认输入限制为 24000、窗口 32768、回答预留 4096、安全余量 1024。这些是当前应用常量，不是所有模型的通用规格。实际部署须匹配所用模型。

长期笔记目录、Skill、工具参数说明也占空间。不同 role 不会让 token 免费；把提示词拆成两条消息也不会自动降低输入量。

项目使用本地 tokenizer 估算序列化材料，无法保证完全复现服务端消息模板，因此估算不是供应商实际计费用量。验收应分别报告二者。

## 5. 确定性移出正文：project_read_messages

这个函数不调用模型，不提炼重点，不修改原始持久化结果。它只创建新的输入视图。

```python
projected = project_read_messages(
    messages,
    max_tokens=4500,
    source_fields={"read_skill": ("name", "resource", "digest")},
    keep_recent=1,
)
```

假设先后读 A、B、C，C 是最近一组。预算不足时，先尝试把 A 正文替换成来源说明；如果已经足够，就保留 B、C 全文。C 默认受保护。同一条助手消息并列请求的多个合格读取结果作为一组保护。

替换后内容示意：

```json
{"name":"A","resource":"SKILL.md","digest":"hash-A","body_omitted":true,"recovery":"如需原文，使用原读取工具及参数补读；此处不代表资料为空"}
```

原工具调用仍在，结果的 tool_call_id 仍在，仅移出正文。assistant 表示模型提出请求，tool 表示程序返回执行结果；二者不是两个模型。

候选必须来自允许的读取工具，能匹配实际调用，并包含要求的来源字段。未知工具或定位缺失的结果不会仅因存在 content 字段就被删除。替换只有确实节省 token 才采用。

这里“旧”按消息顺序判断，不按时间，也没有语义判断“模型已经充分理解”。因此保护最近一组只是启发式。函数也不保证一定压到预算以下，调用方仍须检查。

当前主要在 Planning 使用该机制。聊天会将历史笔记正文转成引用，同时保护本次新读取交互；不能描述成所有场景、所有工具都共用同一清理策略。

## 6. 模型摘要：compact_history 的逐步算法

源码见 [context.py](../backend/src/risk_platform/conversations/context.py)。输入包括旧摘要 previous、尚未覆盖的完整轮次 turns、记忆目录、当前问题，以及当前交互预留 reserve_tokens。

1. 用真实请求组装函数计算整体大小。连当前问题与必要声明都放不下，就明确失败，压缩历史无济于事。
2. 通常输入降至可用预算 85% 即停止，给后续增长留空间。只剩两轮且仍低于硬上限时，不为软阈值强行压缩。
3. 通常保护最近两轮，按时间顺序选择更早的完整问答。如果只剩两轮而仍超硬上限，也允许压缩较早轮次，所以“保留两轮”不是绝对承诺。
4. 按摘要模型自身输入预算组批，不把完整问答切成半轮。
5. 调用 `agent.summarize(旧摘要, 本批轮次)`，得到新摘要。检查返回结构、输出长度，以及重新组装后的输入是否真的减少。
6. 必要时继续下一批；单次函数最多八批，同时受当前请求共享的累计压缩次数约束。
7. 全部处理成功后，事务保存最终摘要与覆盖边界。返回剩余历史消息和新摘要。

```text
原摘要覆盖第1～4轮
本次压缩第5～8轮
结果：新摘要覆盖第1～8轮，保留第9～10轮原文
```

摘要请求不是正常回答请求的全部内容：它主要接收旧摘要和选中的旧交互，不把系统规则、当前问题、全部长期笔记、全部 Skill 一起摘要。

用户在旧消息里说“以后先给结论”，这句话可能进入会话摘要；从个人笔记读取的正文不会直接整体复制进永久摘要。模型最终回答若复述了个人信息，回答文本仍可能成为历史，因此不能声称摘要完全排除任何个人信息传播。

## 7. 摘要到底保存什么

`SUMMARY_PROMPT` 要求保留目标、有效约束、明确决定、否定与纠正、未完成事项及必要定位。它要求区分用户陈述、助手建议、正式结果和未知。

例如原话是“收入缺失率升高，但不能确定它导致风险升高；渠道查询失败”，摘要不能写成“已发现风险升高的原因”。这属于语义质量，JSON 校验无法证明它正确。

当前输出是一份摘要正文，不是持续维护的固定 facts/decisions/todos 多字段工作记录。压缩触发主要来自预算压力，而非每完成一步就额外调用模型。

## 8. 为什么摘要与覆盖边界一起提交

如果先更新“覆盖到第8轮”，却没保存摘要，下一次输入会既不带原文，也没有对应摘要。因此正文和边界必须在同一事务中生效。

摘要调用在事务外进行。返回后重新核对用户访问权限、当前请求状态、摘要版本及边界范围；提交时对会话使用事务锁，防止旧版本覆盖新版本。

失败语义如下：

| 失败位置 | 结果 |
| --- | --- |
| 摘要模型失败或后续批次失败 | 本次新边界不提交，原文保留 |
| 摘要没有缩小请求 | 明确失败，不假装压缩成功 |
| 模型等待期间撤权 | 禁止新摘要提交 |
| 其他调用已经更新摘要 | 版本冲突，不覆盖 |
| 摘要已提交，最终回答失败 | 已提交摘要仍有效 |

这些保证保护存储与关联，不证明摘要自然语言准确，也不意味着聊天进程中途退出已经支持完整自动恢复。

## 9. Planning、Observation 与聊天不能混讲

### Planning

[planning.py](../backend/src/risk_platform/workflow/planning.py) 保存目录、模型调用、读取与压缩事件。`planning_messages()` 根据最近正式保存的 context 事件重建输入。

```python
messages = messages[context["through"]:]
```

这里 through 是已经覆盖的原始消息位置，不是聊天轮数。切片保留边界后的消息，再配合已保存摘要及正文移出标记组装。数据库原始事件不被删除。

当前 Planning 在旧正文投影仍放不下时摘要较早完整交互，并保留近期助手调用组；摘要事件、读取次数和期限都有约束。Skill 方法不能被当成当前案件已经发生的事实。

### Observation

[observation.py](../backend/src/risk_platform/workflow/observation.py) 选择预算内完整结果项并标明省略。`result_page()` 支持读取已保存执行结果，按结果项而非任意字符分页。

`summarize_executions()` 只是确定性生成执行状态与结果类型：成功且有材料、空结果、失败或拒绝。它不调用模型，也不概括业务正文。真正解释由 Observation 模型完成。

Observation 当前保持单次解释，不在里面循环补读。没展示的项不能被引用为已经读过的证据；材料不足应保留问题，交后续规划处理。

## 10. 补读：恢复细节，而不是重新执行业务

| 材料 | 读取入口 | 主要边界 |
| --- | --- | --- |
| 个人笔记 | read_memory | 当前所有权、开关、状态与版本 |
| 会话原文 | read_chat_history | 当前用户及当前会话范围 |
| 历史笔记读取快照 | 指定轮次与读取序号 | 明示历史版本，仍检查当前访问权 |
| Skill | read_skill | 部署目录、固定内容摘要、段落位置 |
| 业务执行结果 | read_execution_result | 案件归属、工具权限、执行 ID、结果项范围 |

读取默认当前笔记版本；续读版本变化要拒绝拼接。读取历史快照不能冒充当前版本。Skill 内容摘要是哈希一类完整性标识，不是模型写的短摘要。

段落分页保留完整段落，结果分页保留完整结果项；单项大到放不下时明确失败，不能截掉一半却宣称读完。补读完成的请求与结果在继续模型调用前保存，便于核查实际用过什么。

当前没有任意文件通用补读，也没有已移出材料的独立目录或通用关键词历史搜索。不能假定每个 CSV、日志、PDF 都能重新取得。无可靠入口的正文不得靠“以后再读”作为删除依据。

## 11. 长期记忆与 MCP 的位置

[personal.py](../backend/src/risk_platform/memory/personal.py) 维护用户隔离的个人笔记，目录用于选择，正文按需读。更新需要读取版本，重复来源避免重复变更，版本冲突不能覆盖别人更新。

会话摘要帮助继续当前讨论，个人笔记帮助跨会话使用稳定偏好。案件经验进入知识库的发布链路目前暂缓，不能把它混入个人偏好维护。

MCP 可以作为远程记忆读取协议，但当前项目尚未接入。它不会自动提供记忆维护、压缩或业务授权。若未来接入，仍需复用当前身份、分页、版本和读取记录边界，不另建一套记忆事实。

## 12. 与 Claude Code 的客观对照

| 方面 | Claude Code 的公开行为 | RiskMind 当前情况 |
| --- | --- | --- |
| 历史保存 | CLI 本地转录及恢复入口 | PostgreSQL 聊天、读取记录和业务账本 |
| 上下文缩减 | 自动或手动摘要，公开说明可能丢细节 | 确定性正文移出＋聊天/Planning 摘要 |
| 持久偏好 | 独立自动记忆笔记 | 数据库个人笔记、修订和读取开关 |
| 方法按需加载 | Skill 描述与正文分开 | 目录、正文读取、固定版本和预算 |
| 压缩后组装 | 启动材料多数重新加载 | 当前规则、任务、摘要、近期交互重新组装 |
| 会话恢复 | 产品有明确恢复能力 | 调查阶段支持恢复；聊天进程中途接续仍有缺口 |
| 反复压缩 | 官方说明会停止反复填满的情况 | 当前请求有次数限制，无完整跨请求失败熔断 |
| 缓存 | 产品主动管理 Prompt Caching | 尚无专项配置及命中验证 |

RiskMind 的数据库授权和版本边界来自多用户业务需求，不代表全面比 Claude Code 更先进。后者面向编码环境，前者需要案件事实和操作权限，两者不能仅按表、字段、校验数量比较。

## 13. 验收证据与尚未证明的事情

测试覆盖摘要失败不推进边界、并发版本竞争、等待期间撤权、原文保留、读取记录不可变、历史版本回查及 Planning 检查点恢复。它们证明特定业务不变量，不能证明所有崩溃点、所有工具或真实模型摘要质量。

真实模型用例位于 [test_context_quality_live.py](../backend/tests/test_context_quality_live.py)，使用合成长会话检查连续摘要、否定和纠正保留、精确原文补读，并输出估算输入、实际用量、调用次数和耗时。由于缺少模型密钥，本轮未执行。关键词断言只是最低门槛，仍须人工审阅摘要是否歪曲原意。

后续缺口是：真实模型质量与成本验证、服务端明确超限后的有界模型重试、聊天进程退出后的可靠接续，以及确有需求时增加材料回查入口。不需要为这些问题先增加万能上下文管理器或额外业务图。

## 14. 阅读代码的推荐顺序

1. [conversations/agent.py](../backend/src/risk_platform/conversations/agent.py)：看 entry_request、SUMMARY_PROMPT、_dialogue、summarize，理解模型看到了什么。
2. [conversations/context.py](../backend/src/risk_platform/conversations/context.py)：看 compact_history，理解选择、摘要与提交。
3. [entrypoints.py](../backend/src/risk_platform/entrypoints.py)：看 prepare_entry 中的读取和记录闭包，理解身份与资源来自哪里。
4. [core/token_budget.py](../backend/src/risk_platform/core/token_budget.py)：看预算、正文投影和段落分页。
5. [workflow/planning.py](../backend/src/risk_platform/workflow/planning.py)：看 planning_messages 与 prepare_plan，理解 Planning 压缩和恢复。
6. [workflow/observation.py](../backend/src/risk_platform/workflow/observation.py)：区分状态归纳、结果分页与模型解释。

理解这套设计的关键是：事实可靠保存，当前输入有界选择，摘要用于延续理解，原文用于核对细节；权限、版本和业务执行权始终由程序决定。
