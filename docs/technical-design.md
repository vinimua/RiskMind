# 信贷风控模型智能监测与自主迭代平台技术设计

版本：1.0（开发基线）。本文件描述目标架构，不代表骨架已实现下述业务能力。

## 1. 目标与边界

平台监测在用信贷模型；发现异常后建立案件，组织多 Agent 调查，提出处置方案，并通过独立验证、规则准入、人工审批、灰度发布与回滚形成可审计闭环。

“自主迭代”指自动发现、调查、提出和验证候选方案，不允许大模型自行批准或直接替换生产模型。阈值、标签成熟期、审批角色和回滚条件按模型及场景配置，不得在代码中硬编码银行生产标准。

## 2. 架构与职责

```text
业务数据／预测日志／成熟标签／模型版本
  -> 监测与告警服务 -> 异常案件 Case
  -> LangGraph 案件图
       + 基础核查（可与知识检索并行）
       + 知识与调查策略 Agent -> 工具计划校验
       + 结构化调查 Agent（独立补查任务可并行）
       + 评估与方案 Agent
       + 候选训练／独立验证 Agent
  -> 版本化规则准入 -> 人工审批
  -> 灰度发布 -> 持续观察 -> 晋级／回滚／结案
```

LangGraph 是唯一业务流程编排器。监测计算、训练、指标验证、权限判断、模型发布及回滚由确定性业务服务执行。Agent 不直接执行任意 SQL、修改规则或发布模型。

### 四类 Agent

| Agent | 输入 | 结构化输出 | 边界 |
| --- | --- | --- | --- |
| 知识与调查策略 | 告警、基础核查、LightRAG 检索证据 | 待验证假设、调查计划、候选工具 ID 和参数 | 只提计划，不执行知识库文字指令 |
| 结构化调查 | 获准计划、只读工具结果 | 分时段、分客群、分渠道及分版本证据 | 工具白名单；每项结果含口径、窗口、样本量、数据版本 |
| 评估与方案 | 已核实证据、历史案例、业务约束 | 观察、数据修复、策略调整或候选训练方案 | 不决定准入或上线 |
| 独立验证 | 候选方案、模型制品、锁定的验证标准 | 质询、验证报告、通过／拒绝／证据不足建议 | 不修改提案或标准；指标由独立程序计算 |

固定核查和知识检索可并行；动态补查先由策略 Agent 提议，再经注册中心校验，独立任务并行执行。补查循环有次数与成本上限，超限转人工或以证据不足结案。

## 3. 知识、工具与规则

- LightRAG 索引已授权的诊断手册、历史案例、模型与变更文档。检索结果要保留来源、版本和引用位置；检索失败不得编造依据。它不保存可直接生效的生产阈值。
- 工具注册中心登记工具 ID、输入模式、权限、范围、超时和数据级别。Agent 只能从白名单选择；执行器必须校验参数和调用身份。
- 版本化规则中心保存获批诊断规则、准入条件、模型特定阈值和回滚护栏。规则执行结果限定为 `PASS`、`REJECT`、`INCONCLUSIVE`，自然语言不能覆盖该结果。

知识库回答“建议查什么及为何”；工具注册中心决定“可以执行什么”；规则中心决定“什么条件下允许进入下一状态”。

## 4. 状态与持久化

主要状态：`OPEN -> INVESTIGATING -> PROPOSED -> VALIDATING -> AWAITING_APPROVAL -> RELEASING -> OBSERVING -> CLOSED`。分支状态：`INCONCLUSIVE`、`REJECTED`、`ROLLED_BACK`、`FAILED`。每次转移记录触发者、时间、证据与规则版本。

每案使用稳定 `case_id` 和 LangGraph `thread_id`。PostgreSQL 保存业务实体和图检查点；图状态保存引用 ID 与少量控制信息，不内嵌大报告或原始敏感数据。审批由图暂停／恢复实现。训练与大批量验证由后台 Worker 执行；图发出带幂等键的任务并保存 `job_id`，受控回调在完成后恢复案件。同一回调、同一图节点重试不得重复执行外部副作用。

## 5. 监测、验证与决策

监测覆盖数据质量、特征及评分分布、客群构成、成熟标签样本的模型效果、服务稳定性。AUC、KS、召回、校准等仅在标签成熟且口径一致时计算；标签未成熟时输出不可判断，不能把漂移直接解释成性能下降。

每次告警固化监测窗口、基准窗口、模型与数据批次、样本量、指标计算代码版本，形成不可变证据快照。训练记录数据、特征、代码、参数、随机种子和制品版本。独立验证服务按锁定标准计算时间外表现、稳定性、校准、关键客群影响和样本充分性；验证失败或证据不足不得进入发布审批。

## 6. 审批、发布与回滚

候选方案先经过机器可执行的准入规则，再由有权限的人员审批。审批与方案、验证报告、规则、制品版本绑定；任一材料变化，原审批失效。

发布服务通过 `ReleaseController` 接口维护候选版、稳定版、流量比例和线上版本。先影子运行或小流量灰度，再逐步晋级。灰度护栏失败时由确定性发布服务恢复上一稳定版本，记录原因并通知责任人；也支持授权人工紧急回滚。Agent 可建议，但不能自由决定切流或回滚。

## 7. 推荐技术栈与部署

- Python、FastAPI、Pydantic、SQLAlchemy、Alembic：API 与业务模块。
- LangGraph + PostgreSQL 持久化检查点：唯一业务编排；不引入 Temporal。
- LightRAG：独立知识服务，通过受控适配器接入。
- Celery + Redis：耗时任务执行，不保存案件状态机。
- MLflow + S3 兼容对象存储：实验、模型版本、数据快照和验证报告。模型别名不等于线上切流，发布由 `ReleaseController` 控制。
- Next.js + TypeScript：案件、证据、方案、审批、发布与审计界面。
- 本地使用 Docker Compose；生产部署依现有基础设施。若使用 Kubernetes，发布适配器可接 Argo Rollouts，但不将它作为 Agent 编排器。

代码组织采用模块化单体 API + 独立 Worker + 独立 LightRAG；先定义接口，不预先拆每个 Agent 为微服务。

## 8. 数据对象与初始接口

核心对象：`Model`、`ModelVersion`、`MonitoringEvent`、`Case`、`EvidenceSnapshot`、`InvestigationTask`、`Proposal`、`TrainingRun`、`ValidationReport`、`PolicyVersion`、`Approval`、`Release`、`AuditEvent`。进入审批的证据、方案、规则、验证报告及制品不得原地覆盖。

首批接口：创建／查询案件；查看证据及 Agent 轨迹；提交／查询方案；触发验证；审批／驳回；查看发布状态；授权人工回滚。后台任务完成回调须鉴权，并按 `case_id + operation_id` 去重。实际路径和字段在 `docs/api-contracts.md` 中逐项确定。

## 9. 安全与交付顺序

生产数据最小权限访问；进入 LightRAG 和大模型的内容分类、脱敏。调查、验证、审批、发布角色分离。Agent 工具调用、规则判断、人工审批、版本切换和回滚均写入审计链。

1. 案件、证据、规则版本、审计和数据库迁移；监测事件建案。
2. LangGraph 案件图、持久化、补查上限与断点恢复。
3. LightRAG 适配器、工具注册中心与四类 Agent。
4. 训练、独立验证、规则准入和人工审批。
5. 灰度、观察、回滚、重复回调及故障注入测试。

端到端验收：评分 PSI 上升时建立案件；并行基础核查与知识检索；发现新渠道占比变化后分渠道复算。标签未成熟时不能声称 KS 下降。若提出重训，必须经过独立验证、规则准入和审批才可灰度；护栏失败自动回滚；所有结论能追溯到证据和版本。
